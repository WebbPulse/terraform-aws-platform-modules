# terraform-aws-staging-access-gate

Puts a CloudFront-fronted staging site, and the HTTP API behind it, behind a sign-in wall for a
fixed list of email addresses. Nothing about the application changes; the gate sits in front of
it and costs a few cents a month at staging traffic levels.

Consumed as `app.terraform.io/WebbPulse/platform-modules/aws//modules/staging-access-gate`.
[WebbPulse-Platform](https://github.com/WebbPulse/WebbPulse-Platform) owns this repository,
publishes it to the private registry, and pushes the `staging_access_gate` and
`staging_access_users` variables that turn the gate on per workspace.

## How it works

```
browser ── https://www.staging.<domain>/anything
             │
             ▼
     CloudFront distribution (the app's existing one)
       ├─ viewer-request function (this module) ── no live session? ──► 302 /_auth/login?next=…
       ├─ default behavior : trusted_key_groups = [gate key group]   (signed cookies required)
       └─ /_auth/*         : Lambda function URL origin, IAM auth via OAC
              login    → Cognito hosted UI (code flow, confidential client)
              callback → exchange code, check email, set CloudFront signed cookies, 302 next
                             cookies are set on Domain=<cookie_domain>, so they also reach the API host

browser ── https://api.staging.<domain>/... with credentials: 'include'
             │  (same-site request, carries the gate's signed cookies)
             ▼
     HTTP API (execute-api endpoint disabled)
       REQUEST authorizer (this module), no identity sources, in order:
         OPTIONS preflight                         ──► allow
         x-origin-verify header matches SSM        ──► allow   (CloudFront, pipelines, health checks)
         CloudFront-Policy/Signature/Key-Pair-Id   ──► allow when the RSA-SHA1 signature verifies,
                                                        the key pair id matches and the policy is live
         otherwise                                 ──► deny (401)
       then, only for route keys in identity_jwt_route_keys:
         Authorization: Bearer <identity access token>
           RS256 signature against the cached JWKS, iss, aud, exp, nbf
                                                   ──► allow, claims in the authorizer context
         otherwise                                 ──► deny (401)
```

- **Cognito user pool**, ESSENTIALS tier, admin-create-only. Every address in `allowed_emails`
  becomes a user and receives an invitation email with a temporary password. Nobody can sign up.
- **Login Lambda** (Node.js 22, function URL, IAM auth) does the OAuth code exchange as a
  confidential client and issues **CloudFront signed cookies** with a custom policy covering
  `https://*<cookie_domain>/*` for `session_hours`. CloudFront verifies them on every request to a
  behavior that lists the module's key group; the Lambda is not on the hot path.
- **CloudFront Function** runs the application's own viewer-request logic first (redirects, URI
  rewrites), then sends browsers without a live-looking session to the login page. API paths get a
  401 JSON body instead of a redirect.
- **HTTP API authorizer** verifies the same signed cookies itself, so the SPA can call
  `https://api.staging.<domain>` directly the way it does in production. It admits a request when
  it is an `OPTIONS` preflight, when it carries the `x-origin-verify` header matching the SSM
  value, or when it presents cookies whose RSA-SHA1 signature verifies against the gate's public
  key, whose `CloudFront-Key-Pair-Id` is this gate's, whose policy has not expired and whose
  `Resource` is `https://*<cookie_domain>/*`. Everything else is refused, so the API host cannot be
  called around the gate. Pair it with `disable_execute_api_endpoint = true` on the API.
  The authorizer has no identity sources and a TTL of 0, so it runs on every request; it is a
  128 MB Node function whose only remote call is an SSM read cached per execution environment.
- **Secrets** (signing key, Cognito client secret, origin header value) live in SSM SecureString
  under `/<name>/access-gate/`. The RSA key pair is generated by Terraform and is therefore also
  in state; acceptable for a staging gate, not for production credentials.

## Enforcing identity access tokens

The gate answers "may this caller reach the API at all". Production answers the separate question
of "who is this caller" with API Gateway's own JWT authorizer, from `http-api`'s `identity_jwt`
input. Staging cannot: a route takes exactly one authorizer and on a gated API that slot is already
this module's. So when `identity_jwt` is set here, the gate's Lambda does both checks, in that
order, for the routes named in `identity_jwt_route_keys`:

```hcl
module "gate" {
  # ...
  identity_jwt = {
    issuer   = module.identity.issuer
    audience = module.identity.audience
  }

  identity_jwt_route_keys = module.api.identity_jwt_route_keys
}
```

`jwks_url` defaults to `<issuer>/.well-known/jwks.json`, `jwks_ttl_seconds` to 300 and
`clock_skew_seconds` to 60. Leave `identity_jwt` null, or the route key list empty, and the function
behaves exactly as it did before: no new environment variables are set, so an existing gate shows no
diff.

### Route keys rather than a second authorizer

The obvious design is a second authorizer resource over the same Lambda, one for gate-only routes
and one for gate-plus-token routes. It does not work. A payload format 2.0 authorizer event does not
name the authorizer that invoked the function. There is no authorizer id in the event and `routeArn`
is a route ARN, so from inside the Lambda the two are indistinguishable.

What the event does carry is `requestContext.routeKey`, and that is the same string the consumer
already wrote: it is the map key in `http-api`'s `routes`. So `http-api` publishes the marked keys as
`identity_jwt_route_keys` and this module matches against them, exactly, with no globbing. One
Lambda, one authorizer, no new resource. `$default` is rejected by a variable validation, because as
the catch-all it would silently enforce on every path nobody has routed.

### Why the route key list travels in the deployment package

A Lambda's environment is capped at 4096 bytes across every variable together, and the API measures
that only at `UpdateFunctionConfiguration`. Terraform's plan never sees it, so an oversized map is a
green plan followed by

```
InvalidParameterValueException: ... the environment variables you have provided exceeded the 4KB
limit. Measured size: 4545 bytes
```

CarModPicker staging hit that at 95 route keys: the list alone serialised to 3600 bytes, against 869
bytes for everything else including the 451 byte signing public key PEM. Neither of the obvious
escapes is available. The list cannot be trimmed, because a key missing from it is a route nobody
enforces, so trimming silently opens routes. It cannot be collapsed to prefixes either, because the
anonymous guard routes sit under the same path prefixes as enforced ones, which is the whole reason
matching is exact.

So the route key list and the signing public key PEM are rendered into `identity_jwt_config.json`
and written into the authorizer's deployment package, which has no such cap. The handler reads the
file next to itself once at import time. The file is one of the `archive_file` source blocks, so its
bytes are part of `output_base64sha256` and therefore part of `source_code_hash`: adding a route key
changes the package hash and Terraform redeploys the code, exactly as it redeployed on an
environment change before.

What stays in the environment is only short scalars whose length does not grow with the consumer's
configuration: the header name, the SSM parameter path, the cookie domain, the key pair id, and the
issuer, audience, JWKS URL, TTL and clock skew. The module's test suite measures that map against
the 4096 byte cap with a 300 key list, so the failure mode cannot come back unnoticed.

Consumers are unaffected: the inputs are the same (`identity_jwt_route_keys` and the key pair the
module creates), and how they reach the function was never part of the module's interface.

### What the application reads

A Lambda authorizer's context always lands under `requestContext.authorizer.lambda`, API Gateway
stringifies every value and it rejects nested objects, so the claims cannot literally arrive where
the native authorizer puts them. They get as close as the platform permits: one JSON string of a
string map, under a key named `jwt.claims`, plus `sub`, `iss` and `exp` lifted out individually for
a caller that wants only those.

| | production | staging |
| --- | --- | --- |
| claims at | `requestContext.authorizer.jwt.claims` | `requestContext.authorizer.lambda["jwt.claims"]` |
| shape | map of strings | JSON string of a map of strings |

One line reads both, and the values are strings on both sides, so `exp` is `"1757200000"` either way:

```python
auth = event["requestContext"]["authorizer"]
claims = auth.get("jwt", {}).get("claims") or json.loads(auth["lambda"]["jwt.claims"])
```

### Verification details

- **`node:crypto`, no dependency.** `archive_file` zips `lambda/authorizer/` as it sits and no
  consumer's Terraform run does an `npm install`, so a library would have to be vendored into this
  repository and maintained by hand. Node 22 imports a JWK with `createPublicKey({ format: 'jwk' })`
  and verifies RS256 natively, and the identity module refuses to sign with anything but RSA.
- **`alg` is read to refuse, never to select.** RS256 or the token is rejected. Taking the verifier
  from the token is how `alg: none` and RS256-to-HS256 confusion get in.
- **JWKS caching.** Kept for `jwks_ttl_seconds` with concurrent fetches deduplicated, force-refreshed
  once on an unknown `kid` so a key rotation recovers without a redeploy, and on a fetch failure a
  stale cache is preferred over failing the request. Fetches have a 2 second timeout.
- **Order matters.** The gate cookie is checked first. A caller with a perfect access token and no
  gate session is still refused, which is the point of a staging gate.
- **`OPTIONS` preflight is exempt**, as it is for the gate, because a browser sends no
  `Authorization` header on it.

## Consumer checklist

The module creates everything it can own outright. The consumer's distribution and API still need
the wiring below, because a CloudFront distribution is a single resource that this module cannot
partially manage. `examples/staging-access-gate-complete` at the repository root shows all of it.

The primary pattern matches production: the SPA is served from the CloudFront distribution and
calls the API on its own subdomain. Only the frontend goes through CloudFront.

1. `module "gate"` with `name`, `cookie_domain` (the staging apex), `site_host` (the www host),
   `allowed_emails`, `http_api_id` and, if the app has one, its
   existing viewer-request logic as `viewer_request_handler_js` defining `function appHandler(event)`.
2. On the distribution:
   - an `origin` for the login function URL using `login_origin_domain_name` and
     `login_origin_access_control_id`;
   - `trusted_key_groups = [key_group_id]` on the default behavior;
   - `function_association` of `viewer_request_function_arn` on the default behavior, the
     `/_auth/*` behavior and the `/index.html` behavior;
   - an ordered behavior for `auth_path_pattern` with the CachingDisabled and
     AllViewerExceptHostHeader managed policies (ids exported as outputs);
   - an ordered behavior for exactly `/index.html` **without** the key group, so CloudFront's own
     custom error response (403/404 to `/index.html`) can still fetch the SPA shell.
3. On the HTTP API: `disable_execute_api_endpoint = true`, and `authorization_type = "CUSTOM"`
   with `authorizer_id = module.gate.http_api_authorizer_id` on every route.
4. In the API's CORS configuration, allow `https://<site_host>` (and any `additional_hosts`) with
   credentials: `allow_credentials = true`, and the origin listed explicitly, since a wildcard
   origin is not allowed with credentials. The gate's authorizer lets `OPTIONS` through so the
   application's own CORS handling answers the preflight.
5. In the frontend build, keep the API base URL pointing at `https://api.staging.<domain>` and send
   requests with `credentials: 'include'` so the browser attaches the gate's cookies. The cookies
   are set on `Domain=<cookie_domain>` with `SameSite=Lax`, so a request from
   `https://www.staging.<domain>` to `https://api.staging.<domain>` is same-site and carries them.
6. Gate every one of those edits on a variable so the production workspace plans a no-op.

### Alternative: proxy the API through CloudFront

The earlier wiring, where browser API calls went through an `/api/*` behavior on the distribution,
still works and its outputs are still exported. Use it when the API has no subdomain of its own, or
when the SPA must call a same-origin path. On the distribution, add an `origin` for the API host
with a `custom_header` of `origin_verify_header_name` / `origin_verify_header_value`, and an
ordered behavior for `api_path_pattern` with `trusted_key_groups = [key_group_id]`, the
CachingDisabled and AllViewerExceptHostHeader policies, and the viewer-request function. CloudFront
then checks the cookies at the edge and the authorizer admits the request on the header. Point the
frontend build at `https://www.staging.<domain>` instead of the API subdomain.

## Inputs

| Name | Description | Default |
| --- | --- | --- |
| `name` | Resource prefix and Cognito domain prefix, e.g. `carmodpicker-staging` | required |
| `cookie_domain` | Staging apex the cookies and signed policy are scoped to | required |
| `site_host` | Host the browser lands on after sign-in; must be under `cookie_domain` | required |
| `additional_hosts` | Other hosts on the distribution allowed to complete the flow | `[]` |
| `allowed_emails` | Who may sign in; each becomes an invited Cognito user | required |
| `session_hours` | Signed cookie lifetime | `12` |
| `auth_path_prefix` | Path routed to the login Lambda | `/_auth/` |
| `api_path_prefix` | Path treated as API traffic by the function | `/api/` |
| `viewer_request_handler_js` | JavaScript defining `appHandler(event)` | passthrough |
| `cloudfront_distribution_arn` | Narrow the login function URL permission to one distribution; leave unset when that distribution consumes this module (cycle) | any in the account |
| `http_api_id` | HTTP API to attach the origin-verify authorizer to | `null` |
| `origin_verify_header_name` | Header CloudFront adds and the authorizer checks | `x-origin-verify` |
| `invite_login_url` | URL in the invitation email | `https://<site_host>/` |
| `mfa_configuration` | `OFF`, `OPTIONAL` or `ON` (software token) | `OFF` |
| `log_retention_days` | Lambda log retention | `14` |
| `identity_jwt` | `{ issuer, audience, jwks_url?, jwks_ttl_seconds?, clock_skew_seconds? }`; turns on access token verification in the authorizer | `null` |
| `identity_jwt_route_keys` | Route keys that must present a valid token, usually `module.api.identity_jwt_route_keys`. Empty means the feature is off | `[]` |

## Outputs

`key_group_id`, `viewer_request_function_arn`, `login_origin_domain_name`,
`login_origin_access_control_id`, `auth_path_pattern`, `api_path_pattern`,
`origin_verify_header_name`, `origin_verify_header_value` (sensitive),
`origin_verify_ssm_parameter_name`, `origin_verify_ssm_parameter_arn`, `http_api_authorizer_id`,
`user_pool_id`, `user_pool_client_id`, `hosted_ui_domain`, `login_function_name`,
`cache_policy_id_caching_disabled`, `origin_request_policy_id_all_viewer_except_host_header`. Plus
`identity_jwt_enforced` (whether the authorizer is checking tokens) and `identity_jwt_route_keys`
(the keys it is checking them on, sorted).

## User experience

First visit: any staging URL redirects to the Cognito hosted UI. Sign in with the invited email
and the temporary password, choose a real password, and land back on the page originally asked
for. After that the site behaves normally for `session_hours`. API calls to
`https://api.staging.<domain>` ride on the same cookies, checked by the API's authorizer rather
than by CloudFront, so the network tab looks the same as production. `/_auth/logout` ends the
session; the API starts answering 401 as soon as the cookies are cleared or the policy expires.

## Known limits

- The hosted UI is Cognito's classic one. Managed login branding needs a resource that only exists
  in AWS provider 6.x. This module now requires 6.x, so that resource is available to adopt; it is
  simply not wired up yet.
- The CloudFront Function checks only that the policy cookie exists and has not expired. The
  signature is verified by CloudFront itself on the key-group behaviors; a forged cookie reaches
  `/index.html` (the SPA shell) and nothing else.
- **CloudFront validates the signed cookie before it runs the viewer-request function.** On a
  behavior with a trusted key group, the key-group check comes first in the request pipeline, so a
  request with no cookies is rejected with a 403 and the function never runs. An unauthenticated
  deep link to `/some/route` therefore does not get the function's 302 to `/_auth/login`. It gets
  the 403, which the consumer's `custom_error_response` turns into `/index.html` with a 200, and
  the SPA shell loads and starts the sign-in from the client instead. The function's 302 only
  fires on behaviors without a key group, which is `/_auth/*` and `/index.html`. This is why the
  unsigned `/index.html` behavior is mandatory rather than a nicety: without it the shell itself
  is behind the key group and the 403 fallback cannot fetch it, so the deep link dead-ends. If
  server-side redirects on deep links are wanted instead of the client-side flow, the key group
  has to come off the default behavior and the function has to become the only check, which
  weakens the gate to a cookie-presence test.
- Callers that are not browsers (a Chrome extension, a deploy pipeline health check) cannot
  complete the hosted UI flow. They call `api.staging.<domain>` directly with the origin-verify
  header, read from SSM.
- The authorizer's environment must stay small. Lambda caps it at 4096 bytes and only measures it at
  apply time, so anything added there that scales with the consumer's configuration reappears as a
  failed apply on a green plan. The route key list and the signing public key are in the deployment
  package for that reason; keep new values out of the environment unless they are short scalars.
- The gate itself answers allow or deny for the whole API, not per route: simple responses with no
  identity sources cannot express finer permissions. `identity_jwt_route_keys` is per route, but it
  only decides whether a token is demanded, not what the token may do. Application level
  authorization is still the application's job; the gate only decides who reaches it.
- The authorizer cannot cache, because API Gateway keys the authorizer cache on identity sources
  and this authorizer has none. Every request invokes it. At staging traffic that is immaterial,
  but it is not a pattern to copy onto a production API.
- The signed cookies are the session for the API as well, so `session_hours` is also the longest an
  API client can go without signing in again. There is no refresh short of another trip through the
  hosted UI.
- A gate failure is easy to mistake for a working site. If CloudFront cannot invoke the login
  function (a missing resource-policy grant, for example), the origin returns 403 and the
  consumer's SPA custom error response turns that into the shell page with status 200. The tell is
  `/_auth/login` answering with `index.html` and `x-cache: Error from cloudfront` instead of a 302 to
  the hosted UI. The module grants CloudFront both `lambda:InvokeFunctionUrl` and
  `lambda:InvokeFunction`; both are required.

## Tests

A harness that exercises the CloudFront Function, the login flow with stubbed SSM and token
endpoint, the authorizer, the identity token verification against locally generated RSA keys and a
stubbed JWKS endpoint, and the size of the rendered Lambda environment. It reaches no network and no
AWS API, and the `node-tests` job in `terraform-ci.yml` runs exactly these three commands on every
pull request:

```
npm install --no-save --no-package-lock @aws-sdk/client-ssm
python3 test/render.py
node test/run.js
```

Run them from `modules/staging-access-gate`, not from `test/`: the Lambda sources require
`@aws-sdk/client-ssm` and Node resolves it upward from `lambda/*/index.js`.

The authorizer suite loads the handler out of a package built the way `archive_file` builds it
(`test/package.js`), because the handler reads `identity_jwt_config.json` from beside itself and
that file exists only inside the archive.
